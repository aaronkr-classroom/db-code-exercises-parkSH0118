## 연습문제

### 1번

문제> 다음 중 물리적 스키마 모델링의 주요 업무에 대한 설명이 잘못된 것은?

1. 논리적 스키마를 기초로 하여 속성의 데이터 타입과 크기, 제약조건 등을 정의한다.
2. 내부 스키마를 ER 다이어그램으로 표현한다.
3. 시스템 성능을 고려하여 물리적 구조를 변경한다.
4. 데이터 사용량 예측 등을 통해서 인덱스나 뷰 설계 작업을 수행한다.

답> 2번

물리적 스키마 모델링은 논리적 스키마를 DBMS가 지원하는 내부 스키마로 변환하는 과정이다. 이 과정에서는 데이터 타입, 크기, 제약조건, 인덱스, 뷰 등을 정의한다. 내부 스키마를 ER 다이어그램으로 표현하는 것은 물리적 스키마 모델링의 주요 업무가 아니다.

---

### 2번

문제> 다음 릴레이션 스키마와 무결성 제약조건을 기초로 하여 내부 스키마를 작성하시오. 단, 각 속성의 데이터 타입과 크기는 속성의 특성을 고려해서 임의로 결정하시오.

```text
도서(도서번호, 제목, 저자, 출판사, 발행일, ISBN, 정가)
```

| No. | 무결성 제약조건 | 제약 유형 | 관련 릴레이션 |
|---|---|---|---|
| 1 | 제목, 저자, ISBN은 널 값을 가질 수 없다. | NOT NULL | 도서 |
| 2 | ISBN은 유일한 값을 가져야 한다. | UNIQUE | 도서 |

답>

```sql
CREATE TABLE book (
    book_no      VARCHAR2(10) PRIMARY KEY,
    title        VARCHAR2(100) NOT NULL,
    author       VARCHAR2(50) NOT NULL,
    publisher    VARCHAR2(50),
    publish_date DATE,
    isbn         VARCHAR2(20) NOT NULL UNIQUE,
    price        NUMBER(8)
);
```

도서번호는 도서 릴레이션의 기본키로 설정하였다. 제목, 저자, ISBN은 널 값을 가질 수 없도록 `NOT NULL` 제약조건을 지정하였고, ISBN은 중복될 수 없으므로 `UNIQUE` 제약조건을 함께 지정하였다.

### 3번

문제> 성능 향상을 위한 물리적 구조 변경 방법 가운데 테이블 추가에 대한 설명이 잘못된 것은?

1. 자주 사용되는 통계 데이터가 여러 테이블에 산재된 데이터를 기초로 하여 생성되는 경우, 별도의 통계 테이블을 생성할 수 있다.
2. 대용량 테이블의 특정 부분만 주로 사용되는 경우 해당 부분만 분리해서 별도의 테이블을 생성할 수 있다.
3. 대용량 테이블의 특정 부분만 주로 사용되는 경우 해당 부분만 복사해서 별도의 테이블을 생성할 수 있다.
4. 하나의 업무 단위가 시간의 흐름에 따라 반복적으로 발생하거나 변경되는 이력 또는 진행 이력이 필요한 경우, 이력 테이블을 추가할 수 있다.

답> 2번

테이블 추가에서 부분 테이블은 원본 테이블의 특정 부분을 복사해서 별도로 생성하는 방식이다. 특정 부분을 분리해서 별도의 테이블로 관리하는 것은 테이블 추가보다는 테이블 분할에 해당한다.

---

### 4번

문제> 성능 향상을 위한 물리적 구조 변경 방법 가운데 테이블 분할에 대한 설명이 잘못된 것은?

1. 한 테이블 안에서 검색 위주의 칼럼과 갱신 위주의 칼럼이 명확히 구분되는 경우, 각각을 별도의 테이블로 분할해서 관리한다.
2. 한 테이블 안에서 특정 칼럼의 보안이 필요한 경우 해당 칼럼만 분할해서 관리한다.
3. 한 테이블 안에서 특정 칼럼의 크기가 매우 큰 경우 이 칼럼만 분할해서 관리한다.
4. 한 테이블 안에서 특별히 빈번하게 갱신되는 칼럼이 있는 경우, 이들 칼럼만 분할해서 관리한다.

답> 4번

수직 분할은 검색 위주의 칼럼과 갱신 위주의 칼럼이 구분되는 경우, 빈번하게 검색되는 칼럼이 있는 경우, 특정 칼럼의 크기가 큰 경우, 보안이 필요한 칼럼이 있는 경우에 적용할 수 있다. 단순히 빈번하게 갱신되는 칼럼만을 분할하는 것은 주요 기준으로 보기 어렵다.

### 5번

문제> 성능 향상을 위한 물리적 구조 변경 방법 가운데 칼럼 중복에 대한 설명이 잘못된 것은?

1. 자주 검색되는 칼럼이 자주 변경되는 경우 해당 칼럼을 중복시킬 수 있다.
2. 다른 칼럼 값을 기초로 하여 계산된 합계, 평균, 개수 등의 파생된 값이 많이 활용되는 경우, 파생 칼럼을 추가할 수 있다.
3. 기본키가 여러 가지 정보를 포함하고 있는데 그 일부가 자주 사용되는 경우, 해당 정보를 분리해서 별도의 칼럼으로 추가할 수 있다.
4. 자주 검색되는 칼럼에 변경이 거의 일어나지 않는 경우 해당 칼럼을 중복시킬 수 있다.

답> 1번

검색 성능을 높이기 위해 자주 검색되는 칼럼을 중복시킬 수는 있지만, 중복되는 칼럼은 갱신이 거의 일어나지 않아야 한다. 자주 변경되는 칼럼을 중복시키면 데이터 불일치가 발생할 가능성이 커진다.

### 6번

문제> 인덱스의 특징이 아닌 것은?

1. 인덱스는 DBMS에 의해 자동으로 사용되고 유지된다.
2. 인덱스는 테이블과는 논리적·물리적으로 독립되어 있다.
3. 기본 테이블을 제거해도 인덱스는 유지된다.
4. 인덱스를 너무 많이 생성하면 오히려 데이터 조작어의 처리 효율이 저하된다.

답> 3번

인덱스는 테이블과 독립된 DB 객체이지만, 기본 테이블이 제거되면 해당 테이블에 생성된 인덱스도 함께 제거된다. 따라서 기본 테이블을 제거해도 인덱스가 유지된다는 설명은 잘못되었다.

### 7번

문제> 인덱스를 선정할 때의 고려 사항을 잘못 설명한 것은?

1. 인덱스가 많으면 갱신 처리를 할 때 비효율적이다.
2. 테이블의 데이터양이 적은 경우 인덱스를 생성하지 않는 것이 더 효율적이다.
3. 검색 효율이 가장 중요하므로 가능하면 많은 인덱스를 생성하는 것이 좋다.
4. 검색 대상이 넓은 경우 인덱스를 사용하는 것은 오히려 비효율적이다.

답> 3번

인덱스가 많으면 검색 성능은 향상될 수 있지만 삽입, 삭제, 갱신 시 오버헤드가 발생한다. 따라서 검색 효율만 고려해서 많은 인덱스를 생성하는 것은 바람직하지 않다.

### 8번

문제> 다음 제품 릴레이션을 테이블로 표현했을 때, 브랜드명 칼럼과 입고일 칼럼에 각각 인덱스를 생성하는 것이 적절한지 여부를 설명하시오. 단, 참고 사항을 고려한다.

```text
제품(제품번호, 제품명, 브랜드명, 원가, 판매가, 수량, 입고일, 담당자id(FK))
```

답>

브랜드명 칼럼에는 인덱스를 생성하는 것이 적절하다. 제품 데이터가 5,000개이고 브랜드 종류가 200개이므로 브랜드명 기준의 평균 분포도는 다음과 같다.

```text
분포도 = 1 / 200 × 100 = 0.5%
```

분포도 값이 10% 미만이고, 제품 검색 시 브랜드명을 주로 사용하므로 브랜드명은 인덱스 후보로 적합하다.

반면 입고일 칼럼은 단독 인덱스 생성에 적합하지 않다. 모든 제품이 매주 월요일에 입고되었고, 데이터 기간이 2024년 10월 7일부터 2024년 10월 28일까지이므로 입고일 값의 종류는 4개 정도이다.

```text
분포도 = 1 / 4 × 100 = 25%
```

입고일은 분포도가 좋지 않으므로 단독 인덱스 후보로는 적합하지 않다. 다만 브랜드명으로 검색한 뒤 입고일 기준으로 정렬하는 일이 많다면, 브랜드명과 입고일을 함께 사용하는 결합 인덱스는 고려할 수 있다.

답>

음식카테고리 칼럼에는 인덱스를 생성하는 것이 적합하다. 음식 테이블의 총 행 수는 2,000개이고 음식카테고리의 종류는 50개이므로 평균 분포도는 다음과 같다.

```text
분포도 = 1 / 50 × 100 = 2%
```

분포도가 10% 미만으로 양호하고, 카테고리별 검색이 빈번하게 발생하므로 음식카테고리 칼럼은 인덱스 후보로 적합하다.

### 11번

문제> 다음과 같은 뷰 정의서를 기초로 하여 고객등급_뷰를 생성하는 SQL 명령문을 작성하시오.

```text
고객(id, 이름, 휴대폰, 주소, 직장명, 누적구매액, 방문일수, 현재등급)
```

고객등급_뷰는 고객의 신규 등급 판정 프로그램에서 필요한 id, 고객명, 구매액, 방문일수, 등급만 조회할 수 있도록 정의한 뷰이다.

### 12번

문제> 뷰 활용의 장단점에 대한 설명이 잘못된 것은?

1. 뷰의 정의를 쉽게 변경할 수 있다.
2. 동일한 테이블에 대해 다른 뷰를 생성할 수 있다.
3. 보안을 위해 DB에 대한 접근을 제한할 수 있다.
4. 복잡한 질의를 단순한 질의로 변환할 수 있다.

답> 1번

뷰는 동일한 기본 테이블을 바탕으로 여러 형태로 만들 수 있고, 보안 목적이나 복잡한 질의 단순화에 활용할 수 있다. 하지만 뷰의 정의는 일반적으로 `ALTER` 문으로 쉽게 변경하는 것이 아니라, 필요한 경우 기존 뷰를 삭제한 뒤 다시 생성해야 한다. 따라서 1번 설명이 잘못되었다.
