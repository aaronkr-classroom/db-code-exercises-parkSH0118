# 10장 실습문제

## 문제

다음은 국내 관광을 전문으로 하는 여행사의 DB 구축을 위한 릴레이션 스키마이다. 함수적 종속 관계를 분석하여 정규화한 뒤, 최종 릴레이션 스키마를 작성한다.

## 1. 초기 릴레이션 스키마

```text
고객(id, 이름, 휴대폰, 주소, 등급코드)
직원(사번, 이름, 생년월일, 연락처, 급여, 담당업무, 입사일)
여행상품(여행번호, 출발지, 도착지, 프로그램, 시작일시, 종료일시, 최소출발인원, 최대인원,
        여행경비, 예약금, 출발여부, 담당직원사번(FK))
관광버스(차량번호, 좌석수, 출고년도)
운전기사(기사id, 이름, 생년월일, 휴대폰, 운전경력, 시급, 계약일, 계약기간)
예약하다(고객id(FK), 여행번호(FK), 예약일자, 예약금결제여부, 여행경비결제여부)
기사배정하다(여행번호(FK), 기사id(FK), 근무시간)
차량배정하다(여행번호(FK), 차량번호(FK))
고객등급코드(코드, 등급, 기준)
업무코드(코드, 업무)
```

## 2. 함수적 종속 관계 분석

### 1) 고객

고객 릴레이션에서 기본키는 `id`이다. 고객 id가 정해지면 고객의 이름, 휴대폰, 주소, 등급코드가 결정된다.

```text
id → 이름, 휴대폰, 주소, 등급코드
```

또한 고객의 등급코드는 등급과 기준을 결정한다.

```text
등급코드 → 등급, 기준
```

하지만 등급과 기준은 고객 릴레이션에 직접 저장되어 있지 않고, `고객등급코드` 릴레이션으로 분리되어 있다. 따라서 고객 릴레이션에는 등급코드만 외래키로 두면 된다.

```text
고객(id, 이름, 휴대폰, 주소, 등급코드(FK))
고객등급코드(코드, 등급, 기준)
```

### 2) 직원

직원 릴레이션에서 기본키는 `사번`이다. 사번이 정해지면 직원의 이름, 생년월일, 연락처, 급여, 담당업무, 입사일이 결정된다.

```text
사번 → 이름, 생년월일, 연락처, 급여, 담당업무, 입사일
```

그런데 직원 릴레이션에 담당업무를 직접 저장하면 같은 업무명이 여러 직원에게 반복해서 저장될 수 있다. 예를 들어 여러 직원이 모두 `예약관리` 업무를 담당한다면, `예약관리`라는 값이 여러 행에 중복된다. 이 상태에서 업무명이 변경되면 일부 행만 수정되어 갱신 이상이 발생할 수 있다.

따라서 담당업무를 직접 저장하지 않고, 업무명을 관리하는 `업무코드` 릴레이션을 따로 둔다. 직원 릴레이션에는 `업무코드(FK)`만 저장한다.

```text
업무코드 → 업무
```

정규화 후에는 다음과 같이 분리한다.

```text
직원(사번, 이름, 생년월일, 연락처, 급여, 업무코드(FK), 입사일)
업무코드(코드, 업무)
```

### 3) 여행상품

여행상품 릴레이션에서 기본키는 `여행번호`이다. 여행번호가 정해지면 출발지, 도착지, 프로그램, 시작일시, 종료일시, 최소출발인원, 최대인원, 여행경비, 예약금, 출발여부, 담당직원사번이 결정된다.

```text
여행번호 → 출발지, 도착지, 프로그램, 시작일시, 종료일시, 최소출발인원, 최대인원,
          여행경비, 예약금, 출발여부, 담당직원사번
```

기본키가 단일 속성이므로 부분 함수적 종속은 발생하지 않는다. 또한 여행상품의 일반 속성들이 다른 일반 속성을 결정하는 구조로 보기도 어렵기 때문에 3NF를 만족한다고 볼 수 있다.

`출발여부`는 예약 인원과 최소출발인원을 이용해 계산할 수도 있지만, 실제 업무에서는 출발 확정 여부를 빠르게 확인하기 위해 저장할 수 있으므로 이 스키마에서는 그대로 유지한다.

### 4) 관광버스

관광버스 릴레이션에서 기본키는 `차량번호`이다. 차량번호가 정해지면 좌석수와 출고년도가 결정된다.

```text
차량번호 → 좌석수, 출고년도
```

모든 속성이 기본키에 종속되므로 별도의 분해가 필요하지 않다.

### 5) 운전기사

운전기사 릴레이션에서 기본키는 `기사id`이다. 기사id가 정해지면 이름, 생년월일, 휴대폰, 운전경력, 시급, 계약일, 계약기간이 결정된다.

```text
기사id → 이름, 생년월일, 휴대폰, 운전경력, 시급, 계약일, 계약기간
```

모든 일반 속성이 기본키에 종속되므로 3NF를 만족한다고 볼 수 있다.

### 6) 예약하다

예약하다는 고객과 여행상품 사이의 관계를 나타내는 릴레이션이다. 한 고객이 특정 여행상품을 예약한 정보를 저장하므로 기본키는 `고객id`와 `여행번호`의 복합키가 된다.

```text
{고객id, 여행번호} → 예약일자, 예약금결제여부, 여행경비결제여부
```

예약일자와 결제 여부 정보는 특정 고객과 특정 여행상품이 함께 정해져야 결정된다. 따라서 복합키 전체에 완전 함수적으로 종속된다고 볼 수 있다.

```text
예약하다(고객id(FK), 여행번호(FK), 예약일자, 예약금결제여부, 여행경비결제여부)
PK(고객id, 여행번호)
```

### 7) 기사배정하다

기사배정하다는 여행상품과 운전기사 사이의 배정 관계를 나타내는 릴레이션이다. 하나의 여행에 여러 명의 기사가 배정될 수 있는 경우를 고려하면, 기본키는 `여행번호`와 `기사id`의 복합키로 두는 것이 적절하다.

```text
{여행번호, 기사id} → 근무시간
```

근무시간은 특정 여행과 특정 기사가 함께 정해졌을 때 결정된다. 따라서 다음과 같이 정리한다.

```text
기사배정하다(여행번호(FK), 기사id(FK), 근무시간)
PK(여행번호, 기사id)
```

### 8) 차량배정하다

차량배정하다는 여행상품에 관광버스를 배정하는 릴레이션이다. 여기서는 여행 하나에 차량 한 대가 배정되는 구조로 보고, 여행번호가 차량번호를 결정한다고 본다.

```text
여행번호 → 차량번호
```

따라서 여행번호를 기본키로 두고, 차량번호는 관광버스 릴레이션을 참조하는 외래키로 둔다.

```text
차량배정하다(여행번호(FK), 차량번호(FK))
PK(여행번호)
```

## 3. 정규화 과정

### 1NF

모든 릴레이션의 속성이 원자 값을 가진다고 볼 수 있으므로 제1정규형을 만족한다.

### 2NF

제2정규형은 제1정규형을 만족하면서, 기본키가 아닌 모든 속성이 기본키 전체에 완전 함수적으로 종속되어야 한다.

복합키를 가지는 주요 릴레이션은 다음과 같다.

```text
예약하다(고객id, 여행번호, 예약일자, 예약금결제여부, 여행경비결제여부)
기사배정하다(여행번호, 기사id, 근무시간)
```

`예약하다`에서 예약일자와 결제 여부는 고객id와 여행번호가 함께 정해져야 결정된다. 또한 `기사배정하다`에서 근무시간은 여행번호와 기사id가 함께 정해져야 결정된다. 따라서 부분 함수적 종속 문제가 없으므로 2NF를 만족한다.

### 3NF

제3정규형은 제2정규형을 만족하면서, 기본키가 아닌 속성이 기본키에 이행적으로 종속되지 않아야 한다.

고객 등급의 경우 `등급코드 → 등급, 기준`의 종속 관계가 있으므로 등급과 기준을 고객 릴레이션에 직접 저장하면 이행적 종속이 생길 수 있다. 하지만 이미 `고객등급코드` 릴레이션으로 분리되어 있으므로 문제가 없다.

직원 업무의 경우 직원 릴레이션에 담당업무명을 직접 저장하면 업무명이 반복될 수 있다. 따라서 담당업무를 `업무코드(FK)`로 변경하고, 실제 업무명은 `업무코드` 릴레이션에서 관리하도록 분리한다.

```text
직원(사번, 이름, 생년월일, 연락처, 급여, 담당업무, 입사일)
```

위 구조를 다음과 같이 수정한다.

```text
직원(사번, 이름, 생년월일, 연락처, 급여, 업무코드(FK), 입사일)
업무코드(코드, 업무)
```

이렇게 하면 업무명 반복을 줄일 수 있고, 업무명 변경 시 한 곳만 수정하면 되므로 갱신 이상을 줄일 수 있다.

## 5. 정리

초기 스키마는 대부분 엔티티별로 분리되어 있어 3NF에 가깝다. 다만 직원 릴레이션의 `담당업무`는 같은 업무명이 여러 직원에게 반복될 수 있으므로 `업무코드(FK)`로 변경하는 것이 적절하다. 고객의 등급 정보는 이미 `고객등급코드` 릴레이션으로 분리되어 있으므로 고객 릴레이션에는 `등급코드(FK)`만 유지한다. 예약, 기사배정, 차량배정 릴레이션은 각각 고객과 여행상품, 여행상품과 기사, 여행상품과 차량 사이의 관계를 나타내도록 구성한다. 최종적으로 중복을 줄이고 갱신 이상을 줄일 수 있는 3NF 중심의 릴레이션 스키마로 정리할 수 있다.
